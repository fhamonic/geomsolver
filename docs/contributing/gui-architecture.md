# GUI architecture

The GUI is built in two layers. The library `gs_app` holds everything except pixels and native widgets: the document and its undo stack, the selection, the canvas's picking and drawing, the menus and shortcuts, and what every panel and dialog shows and does. A front-end draws `gs_app` with one GUI toolkit. Today's front-end uses Dear ImGui; a wxWidgets one would replace that layer only, and reuse the behaviour, the undo history and every list's content unchanged.

Read this page before you change the GUI. It tells you where a change goes, what the ImGui front-end may and may not do, and what another front-end has to implement.

## The layers

```text
  front-end (ImGui today)     views, a Painter, input translation, the main loop
        │  draws, feeds pointer input, runs actions and presenter operations
        ▼
  gs_app (no toolkit)         Document, Selection, App, actions, CanvasController,
                              display list, presenters, dialogs, change signals
        │
        ▼
  gs_engine, gs_solve,        parser, compiler, evaluator; NLP, multistart, service;
  gs_sketch                   the sketch solver
```

| Layer | Sources | Links | Namespace |
| --- | --- | --- | --- |
| `gs_engine`, `gs_solve` | `src/gs/engine`, `src/gs/solve` | | `gs` |
| `gs_sketch` | `src/gs/sketch`, `include/gs/sketch` | `gs_engine`; Eigen, privately: its headers name no Eigen type | `gs::sketch` |
| `gs_app` | `src/gs/app`, `include/gs/app` | `gs_engine`, `gs_solve`, `gs_sketch` | `gs::app` |
| ImGui front-end (`geomsolver`) | `src/front/imgui`, `include/front/imgui` | `gs_app`, GLFW, GLEW, ImGui, ImPlot | `gs::front::imgui` |

Two tests keep the line between the layers:

- **`gs_app_toolkit_free`** fails when a file of `include/gs/app`, `src/gs/app` or `tests/app` includes an ImGui, ImPlot, GLFW, OpenGL, wxWidgets or front-end header (`tests/app/toolkit_free.cmake`). The link rule alone is not enough: every target sees all of `include/`, so a front-end header would compile.
- **`test_app`** links `gs_app` only. Every behaviour of the GUI is tested there, headless.

## The patterns

### The Document is the command processor

Every change to the instance goes through `Document`. `apply(EditBatch)` applies its operations, recompiles once and records one undo step; `edit()`, `erase()` and `revert()` build such a batch. A drag is a gesture: the moves between `begin_gesture()` and `end_gesture()` are one step. A front-end never edits the `Instance` itself, and calls none of these directly either: it goes through an action or a presenter operation. The one exception is ending a gesture the toolkit lost track of (the safety net of the ImGui frame below).

An edit recompiles at once. Whatever was read from the document before it may be stale, and a JSON path kept across a change of `path_generation()` (an erased array entry, a rename, an undo) may name another entry.

### The sketch: two models and a session

A document with a `sketch` section has two models. `model()` is the design-mode compile (the Drawn binding: every sketch value a constant), which the scene, the lists and the solver use as they always did. `sketch_model()` is the sketch-mode compile (the Free binding: each free sketch value a column of q), made by `gs::sketch::settle()`, which also solves the geometry constraints. Every compile of such a document settles first:

- `apply()` settles and **writes** the values it moves when the batch touches `sketch`, `params`, `geometry`, `include`, `let` or `constraints` (a rename may touch any; a note, a helper flag, a constraint's label or the sketch's extent, which no settle reads, settles in a dry run), or asks for it (`EditBatch::solve_sketch`, the action `sketch.solve`, "Solve sketch"). The write is part of the batch's undo step, decided after the settle: a Solve sketch that moves nothing records no step. `SettleOptions::previous` is the last sketch model, so a dimension typed far from its value is reached by continuation. A settle that wrote is followed by a sketch-mode compile of the written values, which `sketch_model()` and `settled().q` then hold, as a load of the saved file would: `settle()` compiled its own model before the write, and an arc's angle scale and polyline come from its drawn radius, so a drag or a monitored row on that model would follow the old radius.
- Load, undo, redo, an edit of anything else (a criterion, a display item, a design entry), `recompile()` and Save As settle in a **dry run**, which writes nothing: a file edited by hand is drawn as written, and its sketch message says "Not solved". The dry run keeps the sketch model in step with the design-mode one, whose `x` it reads (`sketch_x()`) in the same charts. A dry run of the six sections as the last settle saw them (an edit elsewhere, its undo) is not solved again, since `settle()` is a pure function of them: only the sketch model is compiled, and the diagnosis is kept for the new generation. It is solved again when the model's constraints, Solve groups or columns do not line up with the last one's (a design entry a constraint reads, gone), and at `load()` and `recompile()`.
- A settle whose compile fails keeps the last good sketch model, as a failed compile keeps `model()` (`sketch_stale()`). Its diagnostics join the design compile's, once each. A document without a sketch settles nothing and never emits `Sketch`.

`sketch_generation()` moves each time the sketch model is replaced or dropped. A diagnosis (`SketchDiagnosis`) is tagged with the generation it was computed for and holds the model it names rows and elements of; `set_diagnosis(generation, result)` drops a result for any other generation. A settle whose components have at most `Options::sync_columns` columns (150) is diagnosed by the commit itself; a larger one by `SketchSession`.

`SketchSession` (`App::sketch()`, owned by App like the `SceneCache`) holds what no commit needs:

- **A drag**, headless: `begin(gesture, label)` from a `gs::sketch` gesture (`drag_point()`, `drag_body()`, ...; the Properties drags of a sketch element's or a body's free values too, through their builders' `drag_started()`, `dragged()` and `drag_ended()`, and a value typed into one (`set()`) as a single frame of its drag, a body's member with the Edit body gesture of its body), `move(targets)` per frame, `end()` at the release, which first goes on towards the last frame's targets while that converges (a frame's damped step stops short of them, so a typed value would otherwise be written as 1.0000012 for 1), then applies the values that moved (`gs::sketch::written_values()`) as one batch under its label, one undo step, or nothing when nothing moved, and `cancel()`. The drag edits no document while it runs: `scene()` is the sketch-mode scene at the live values, which the canvas draws. A new sketch generation (any commit, an undo) or a sketch that stops compiling cancels it: its q belongs to the model it started on. The actions Undo and Redo release an open drag first, as `Document::undo()` and `redo()` end a gesture: the drag is its own step, which an undo then takes back, and both actions are enabled during a drag with an empty history. Delete releases it first too, as `Document::apply()` ends a gesture: the drag's commit would otherwise come at the release, after the plan the Delete dialog shows, and drop it; a deletion applied under the drag would cancel the drag. `gesture_diagnosis()` is the diagnosis of the gesture where it started, with the gesture's held columns.
- **The monitored statuses** (`monitored()`): the inequalities and the other Design groups over the sketch, evaluated after each drag frame and at `tick()` after a commit, a move of `x` or a drag's end, never enforced. Until that `tick()`, `busy()` is true.
- **The diagnosis worker**: one `std::jthread` job at a time, which diagnoses with a copy of the `System` (it shares the immutable model) and copies of q and the left-out constraints, so it shares nothing mutable with the GUI thread. `App::tick()` starts it 150 ms after the last commit and polls it; its result goes to `Document::set_diagnosis()`, dropped there when a commit came since. The worker is off by default (`set_worker()`): the diagnosis then runs at the next `tick()`, on the GUI thread, so that a scripted run and the tests check and draw the same every time. An interactive front-end turns it on.
- **The sketch message** (`message()`): one at a time in FreeCAD's order (empty, conflicting, malformed, redundant, did not converge, not solved, free DOFs, fully constrained), a list of parts, each a link when it selects something: a constraint's name selects it, "3 free DOFs" the elements that can still move, "tv: frame not anchored" the body; a list is cut after five names, "and 12 more" selecting the rest. While the diagnosis of the last change runs, the previous message of the same document stays, greyed (`greyed`, shown in `Tone::Dim`); while the sketch does not compile, its last good message stays, marked `stale` and greyed too. `dimmed()` says why, for the tooltip. Every kind after "did not converge" waits for the diagnosis, so a redundancy is said before a drawing off its constraints.

### Actions

`App` registers every command in an `ActionRegistry`: an id (`edit.undo`), a label function ("Undo move A"), a toolbar button's `caption` when the label is too long for one (the context menu's "Add clearance(tv, couch) >= ... for all tau" is the button "Add constraint..."), its chords, a scope (Global, Canvas while the pointer is over it, Panel while a panel has the keyboard), the flags `exact_mods`, `in_text`, `in_field`, `repeat` and `in_popup`, the `enabled`, `checked` and `run` functions, and a `tip` for the tooltip of its menu entry or button.

A chord without modifiers fires with any modifiers held (Shift+Del deletes), unless the action has `exact_mods`: then each chord needs exactly its own modifiers. Every Canvas-scope action and every tool action has it, so that Shift+C starts Circle and does not also run Coincident's C, and Ctrl+S saves without running Symmetric. `ActionRegistry::matches(action, focus, held, key)` states the whole rule, enabled or not; `run_pressed()` applies it, in the `KeyFocus` that `App::key_focus(scope, typing, popup)` makes of what the toolkit says. It adds `field` while a tool's value field waits for the keyboard and no text field has it (`ToolHost::field_waiting()`, from the seed, or a digit that asks the keyboard back, to the frame the view's field takes it; not while a text is left in a field that lost it to a panel, when every key works): then only the `in_text` actions and the four `in_field` ones fire, `app.escape`, `tool.finish`, `tool.back` and `tool.field`, which act on that field as its own <kbd>Esc</kbd>, <kbd>Enter</kbd>, <kbd>Backspace</kbd> and <kbd>Tab</kbd> would, so that the letters of `30cm` typed fast after the seed go into the field and start no tool. `tests/app/test_actions.cpp` enumerates every key and modifier set for each focus a front-end produces (Global, with Canvas, with Panel, with both, typing or not, a popup open or not, a field open or not): no press fires two actions but `tool.finish` and `list.activate` on <kbd>Enter</kbd>, which `tool.finish` leaves to a list that has the keyboard, unless the pointer is over the canvas.

<kbd>Esc</kbd> is one action, `app.escape`, which takes one step of the chain wherever the pointer is (`App::escape()`): a text field and a popup handle their own Esc before it (it is neither `in_text` nor `in_popup`); then a tool drops the shape it has in progress, a polyline finishing it open; then a tool with nothing in progress quits; then the selection is cleared. `edit.clear_selection` keeps its menu entry, without a chord. `App::menus()` lists the menus as action ids and submenus (View > Panels), and `App::context_actions()` the context menu of the selection: the enabled actions only, in groups separated by `""`. A front-end builds its menus and its shortcut handling from these; it never decides itself whether Undo is enabled or what Delete does. An action over several selected entries is one `EditBatch`, one undo step.

### Edits of the sketch

Every edit of a sketch that is no formula (plan 4.6, 4.10) is a function of `sketch_edits.hpp` that reads the document and returns a `SketchEdit`: one `EditBatch`, the constraints it deletes with it (`removed`), the formulas it leaves for the user to check (`check`), the entries it creates (points, a tool's element or constraint), the point a merge erases, or a `refusal`. `App::apply_sketch_edit()` applies it as one undo step, selects the entries it created, drops the merged point and the slots of the elements it edited from the selection, and puts its `report` or its refusal in the notice (`App::notice()`, below). Tests call the functions directly; the actions call them through `apply_sketch_edit()`, and the tools through `ToolContext::commit()`.

- **Merge** (`merge_points()`, the action `sketch.merge`) substitutes the first selected point for the second through `substitute_entry()`, then erases the second. The cascade below works on the substituted document: a segment or box whose two ends become one point is erased with its constraints, the survivor kept although that element was its only user (`Cascade::keep()`), and the report names the elements erased with their reasons before the constraints, a polyline loses the second of two equal vertices with its edge indices mapped onto the vertex they became. A constraint of a recognised kind (`match_kind()`) that would read a point twice (two of its points one, a segment of it collapsed, a point at an end of its own line, two segments one) is erased; a Formula-kind constraint that would do the same (two arguments of `dist`, `coincident`, `segment`... or of a subtraction written alike after the merge, not before) refuses the merge.
- **Merge into a derived point** (`merge_into()`, the Coincident tool on a point element and a point of another element of its frame) substitutes the derived point's accessor (`end(door)`) for the point element, then erases it, with the same cascade. It refuses a fixed point, which an accessor cannot hold fixed, and a derived point drawn from the point itself, through the slots and values of the elements its accessor reads, since the substitution would make it read itself. It takes an `Instance`, not a `Document`, so that it can merge into an element a batch is about to add.
- **Detach** (`detach()`) gives each element that holds a shared point, or a selected slot, a fresh point at the drawn position of that slot (`SketchSlot::local`, evaluated in the sketch model), in the frame of the element that holds it: it needs a sketch that compiles.
- **Vertices** (`delete_vertex()`, `insert_vertex()`) rewrite every `edge(e, i)` and `vertex(e, i)` with a literal index in every expression (the parser's spans), erase the recognised constraints on the edges that a removal or a split makes go, and list the Formula-kind ones and the non-literal indices in `check`.
- **Fix, driving, side**: `fix_sketch()` (shared with the sheets: a freed expression is written as its number), `set_driving()`, `flip_side()` (the matcher's side span negated; `line_dist(P, S)` gains `, -1`; a `tangent_at` whose segment ends at the joint on one side and at a free point of its frame on the other has that point mirrored through the joint in the same batch, since the wrapped row of the flipped tangent starts on its cut; `settle()` then walks no row the drawing already holds from its old value).

A selected slot is `{Element, "L1", "to"}`: `sub` is `from`, `to`, `center`, `points i` or `corners i` (`slot_sub()`, `slot_path()`). It goes from the selection when the slot no longer exists, and when an edit changes its element, whose slot `i` may then hold another point.

**The delete cascade.** `plan_delete()` gives the selected sketch elements, bodies and vertex slots to `sketch_cascade()`, which works on a copy of the document whose erased entries are only marked, so that every path it reads keeps its meaning, and erases them last, each array from its end:

- an element whose slots or values use an erased element or member goes too, with the reason (`DeletePlan::taken`: "top (it uses tv.c)"); a polyline's or polygon's slot loses the vertex instead (`vertices`), and below 2 or 3 points the element goes;
- a body takes its members, and so its link arms;
- a point only erased elements held, of their frame, and that no formula names, goes (`orphans`);
- a constraint of a recognised kind that names what goes, or reads an edge or a vertex that goes, is erased (`removed`); a Formula-kind constraint stays and is excluded (`broken`), and one over a shifted index is listed (`check`).

`DeleteRequest` asks first when the delete breaks a formula, takes an element the user did not select, or leaves a formula to check; it lists the rest in its groups. Deleting an element with the points only it held asks nothing.

### Tools

A tool of the canvas (`Tool`, plan 4.2) is a state machine that never calls a toolkit: `ToolHost` (`App::tools()`) feeds it `ToolEvent`s (Move, Press, Release, Key, and Cancel for a press that ended without its release; the pointer in the tool's frame, the view's scale, the button, the click count, whether the press was a drag, the modifiers and the `SnapResult` of the pointer, below), its start (`on_start()`, where a select-first constraint tool applies to the selection and quits), the texts applied to its value fields (`on_field()`), a field closed unapplied (`on_field_closed()`: Esc in it, Esc taking a text left in it, a press with nothing typed into it) and the document's changes (`on_document_changed()`). The characters typed over the canvas are no event: `ToolHost::typed()` seeds the fields with them. It shows its `hint()` (the status bar's tool segment), its methods (<kbd>M</kbd> cycles them), its `fields()` and its `preview()` (shapes and suggested constraints, which the display list draws in the roles `Preview` and `Suggestion`; a point's `label`, the slot it will share or derive, `E` or `mid(L1)`, and the glyphs of one anchor side by side). It commits through its `ToolContext`: `commit(SketchEdit)` is `App::apply_sketch_edit(edit, true)`, one undo step whose new entries are selected, the first revealed before the edit's report is set (a reveal moves the selection's generation, which the notice lasts for); the context also gives `select(key)` (the Point tool's press on a derived point), `open_field(id, text, select)` (a field the tool opens itself, seeded and its text selected, Smart Dimension's editor), `evaluate(text, unit)` (a typed value compiled as a probe: a number, a param or a constant expression; a bare number in an angle field is written in degrees; a value that reads a design variable or a sweep is refused), the toolbar's options and `try_constrain()` (below).

`StateTool<State, Method>` gives a tool FreeCAD's `DrawSketchDefaultHandler` rules: states from the first to `End`; a move tracks (preview, measured values), a left press places and advances; reaching `End` commits one batch, then the tool restarts (continuous mode, on by default) or asks to be quit (`done()`); a field applied is locked and the pointer no longer drives it, a field of an earlier state (`ValueField::placed`, still shown at its anchor) returns to that state when applied, and once every field of the state is set the state completes as a press at the last pointer position would; Esc or a right click drops the shape (`drop()`). A field applied shows what the document is given (`parse()`, `ToolContext::evaluate()`: `30` typed in an angle is `30deg`), and `typed_text()` gives it to the dimension the tool writes.

**Snapping.** For each event to the tool, the canvas asks a `Snapper`, built from the scene it draws, under the tool's `snap_filter()` (plan 4.4). Its first hit, in this order: a point within 8 pixels, the nearest (a point element of the world, a point derived from a world element through its accessor, `end(door)`, `vertex(shelf, 2)`, a body's point member, `tv.c`, a point of the room's geometry, `pillar` or `vertex(couch, 2)`; at one distance a point element before a derived point, so that a box corner written as `S` gives `S`); a segment's or an edge's middle within 8 pixels, `mid(L1)`, `mid(edge(B, 2))`; a line, a circle or an arc within 6 pixels, of the sketch or of the geometry; the origin within 8 pixels, then an axis within 6; the grid's minor lines when the option `grid_snap` is on, whether View > Grid draws them or not. What an eye or the View menu hides is otherwise no target, nor are a body's elements other than its point members. <kbd>Ctrl</kbd> held is freehand: the canvas asks nothing, and the tool suggests nothing. The `SnapResult` gives the slot text that shares or derives a point (`ref`), or none for a new point, the target, and for an edge or an axis what the new point lies on (`on`, `round`); `snap_constraints()` turns it into the suggestions of a new point: `on_line(P, L1)`, `on(P, K1)`, `P.y == 0`, `P.x == 0`. While a tool is active, the snapped target is the canvas's hot key, outlined as a hovered entry is. A scene of another model than the one the tool's last event was snapped in (a commit, an undo) makes `update()` give the tool a move at the pointer, though it did not move: the preview after a commit snaps to the point just created, as the next click does, and a constraint tool's hint and glyph speak of the line just constrained. An immediate-mode front-end needs nothing beyond calling `update()` every frame; an event-driven one calls it again with the last pointer input, no motion, and `app.scene(false)` on `App::changed()` with `Instance`, `Model` or `Sketch` while a tool is active, or the status bar keeps the hint from before the commit until the pointer moves.

**The commit of a shape.** A creation tool commits through a `ShapeDraft`, made from its `ToolContext` (and so, from Edit body on, in its frame), and names what its preview shows through one too (`next_point_name()`, `next_element_name()`), as a constraint tool writes its formula (`constraint_edit()`, with the `keys` of its `Proposal`): every name and path a tool writes is the draft's, the one place Edit body changes: a point placed by a snap that has a `ref` is that text in the slot, any other is a new point `P<k>`, a helper one when asked (Box's centre); a constraint the shape is made with (`constraint()`, Box's `symmetric(P1, P2, Pc)`) is written as asked, before the dimensions; elements are named with the tool's prefix (`L<k>`), constraints with theirs (`d<k>`, `a<k>`, `h<k>`, `v<k>`, `on<k>`), each the first that neither the document's namespace, its constraints, nor the draft use. The typed values are driving dimensions (open question Q2), `dimension()` returning the name it gives and writing the `keys` it is given beside the formula (Smart Dimension's `label`); the suggestions come last, those of the first point, then the next, then the direction. `try_constrain()` (SolveSpace's TryConstrain, plan 4.4) settles a copy of the document with all of them in a dry run, solving and ranking only the components they touch (`SettleOptions::only`: the others keep their drawn values, so its cost does not grow with them), and reads each off the ordered QR: a suggestion that depends on the rows before it, conflicts with them or is malformed is left out silently; one whose component has more than `sync_columns` (150) columns, or whose solve did not converge, has no fresh rank and is left out too, which the report names; a component of at most `sync_columns` columns that `settle()` did not rank, its polish short of its target (a drawing a commit's settle left within its tolerance, where a dependent row is off its set by that much), is ranked by the diagnosis instead; a dimension dependent there is tested once more at the second point (`System::diagnose()` of its own components alone, its `only` taking the dimensions' paths as `SettleOptions::only` does), and only one dependent at both becomes a reference dimension, `"driving": false`, with the report "d3 would over-constrain the sketch: added as a reference dimension" (open question Q3, `ToolOptions::dependent`: `Driving` keeps it driving for the diagnosis to report). A dimension that holds and whose rows no component holds once settled (they read no free parameter, every one they read is held, or their gradient is zero everywhere: the side of a box `S`, `S + vec(1.2, shelf_d)`) is never dependent, no rank seeing it: `Tried::fixed` makes it a reference whatever `dependent` says ("d1 reads nothing that can move: added as a reference dimension"), as FreeCAD does; one off its value is Malformed (`Tried::stuck`). Then one batch is applied, one undo step, whose label names the element ("add segment L3"); the first shape of a `/1` file sets `"format"` to `/2` in that batch, and is refused when the file holds keys that `/1` ignores with a warning and `/2` refuses ("this file holds keys a /2 file may not: constraints[0].release"), since the compile would then leave out the item that holds one. The Auto constraints option (`ToolOptions::auto_constraints`) off suggests nothing, and leaves the ties a shape is made with; Helper (`helper`) writes `"helper": true` on the elements.

**The Segment tool** (`SegmentTool`, `tool.segment`) places A, then B. Its methods are "two points", where B snaps to anything, and "point, length, angle", whose `snap_filter()` refuses the kinds that share a point. Its fields are the length and the angle (dimensional), and A's x and y (positional); a typed length or angle puts B on that circle or ray and refuses every snap, a typed x or y makes A a new point. A new B within 2 degrees of an axis suggests `horizontal(L)` or `vertical(L)` and is put on that axis exactly, so that the commit's settle moves nothing. A second press on A places nothing; Enter places B at the pointer.

**The Point tool** (`PointTool`, `tool.point`) has one state, Place, with the positional fields x and y: a press places a new point `P<k>` (`ShapeDraft::element()`, so that the point itself is the entry created, selected and revealed), with its snap's suggestions and a dimension per typed coordinate. On a snap that shares a point (`Point`, `Derived`), the press selects that point through `ToolContext::select()` and places nothing; its `snap_filter()` refuses `Midpoint`, which has no selection key of its own (the snapper's target is the edge), so the edge under it is taken instead.

**The Polyline tool** (`PolylineTool`, `tool.polyline`) places its first vertex in First, then each next one in Next, which `place()` keeps by returning false after `StateTool::release(Next)` has freed the edge's fields for the next edge; a press on the first vertex (within 8 pixels, or its snap's slot when it is shared) with three placed returns true, and End commits a `polygon`; `finish()` (Enter) and `drop()` (Esc, a right click) advance to End open with two vertices or more, `drop()` restarting with fewer or when the commit is refused; `back()` (Backspace) pops a vertex. Its per-edge values and directions are kept on the vertex that ends the edge and written at the commit as `len(edge(PL1, i))`, `angle(edge(PL1, i))` and `horizontal(edge(PL1, i))`, since only the end tells `PL<k>` from `PG<k>`. In a state placed again, Tab after its last field opens the next round's first field (`Moved`), the next edge's length.

**The Box tool** (`BoxTool`, `tool.box`) places a first point, then a corner, with the fields width and height, written `len(edge(B1, 0))` and `len(edge(B1, 1))`: `Op::Box` puts vertex 1 at the second corner's x and the first's y, so edge 0 runs along x whatever the corners' order. Its methods are "two corners", the box's `corners` as placed, and "centre and corner", whose first point is the centre, a new helper point unless it snapped to one (`ShapeDraft::point(..., helper)`), whose corner is the box's vertex 2 and whose vertex 0 is a new point mirrored through the centre, kept there by `symmetric(P2, P3, P1)`, a constraint the shape is made with (`ShapeDraft::constraint()`), which `try_constrain()` neither tests nor drops. A typed value puts the corner that far along its axis on the pointer's side, half as far from the centre. A corner with the first point's x or y, or within half a pixel of either, places nothing, and no direction is suggested: a box is axis-aligned in its frame.

**The Circle tool** (`CircleTool`, `tool.circle`) places the centre, then a point of the rim, with the field radius, `radius(K1) == v`. In Radius its `snap_filter()` takes points (`Point`, `Derived`, `Midpoint`) and the grid only: the circle then passes through the point, held by `on(E, K1)`, a constraint the shape is made with, as the Arc tool's start is tied.

**The Arc tool** (`ArcTool`, `tool.arc`) has the states Centre, Start, Sweep and End, since reaching End commits. Start takes the radius and the start angle from the pointer, or from the fields radius and start; Sweep turns from the start with the pointer, taking of the two angles to it, one each way round, the nearer to the last sweep, so that it passes the −x axis continuously and starts again from 0 after a whole turn (FreeCAD's rule), or the field span, a magnitude whose direction the pointer gives. A clockwise sweep is stored with its ends swapped, `start` being the start angle minus the span, written in (−π, π]: the point placed in Start is then `end(Arc1)`, and a start angle typed is written `end_angle(Arc1) == a`. The start is tied to a point it snapped to by the Coincident tool's rule (`coincidence()`), since an arc's end is derived and shares no point, and the tie is a constraint the shape is made with, whatever Auto constraints says and whatever the size of its component (the Steps 9–10 ruling): a free point of the world is merged into it in the same batch (`ShapeDraft::merge_into()`, on the document the arc is added to; the arc's own centre drawn from the point, or a merge the cascade refuses, falls back to the formula), a fixed point, a derived one or a middle gets `coincident(start(Arc1), E)` (`co<k>`), a body's member the pin (`pin<k>`); a line, an axis or the origin give `snap_constraints()` written on `start(Arc1)`, suggested; in Sweep the `snap_filter()` takes nothing. The preview draws the arc as a `Path` with a vertex every 2 degrees or less.

A press that would place nothing (a segment or an edge of no length, a circle or an arc of no radius, a box of no area, an arc of no span, a polygon of two points) is refused, and from then on, while the pointer stays where a press places nothing, `hint()` says why ("Box, two corners: a box needs a width and a height"); not before such a press, since a state's pointer starts on the point just placed. The fields of the creation tools hold magnitudes (plan 1.5): a length, a width, a height or a radius is positive, a span is in (0°, 360°), and a refused value names the rule ("a radius is positive"); an angle of a segment or of an arc's start, and a point's x and y, are signed. <kbd>Enter</kbd> (`finish()`) places the next point of a shape under way at the pointer, as a press would, and ends a polyline open. A tool's `hint()` names its method when it has two, then what the state waits for and the field a digit opens ("Box, two corners: pick the opposite corner, or type the width"); a first state names <kbd>Tab</kbd> when it has positional fields and <kbd>M</kbd> with the next method when there is one ("; M: centre and corner"). `provide_creation_tools()` plugs the six tools in, from App's constructor.

**Picks.** A constraint tool picks elements and places no point: its `snap_filter()` takes nothing, and its `pick_filter()` names the kinds of `ToolPick` its state takes: Vertex (a point element, a body's member, or a point derived from an element: an arc's start and end, a box's corner, a centre or a slot's constant that names no point), Line (a segment, an edge of a polyline, polygon or box), Round (a circle, an arc) and Body. For each event to such a tool, the canvas asks a `Picker`, built from the scene it draws, and puts its first hit in `ToolEvent::pick`: a vertex within 8 pixels, then a line or a round within 6, the nearest, a point element before a derived point at one distance. A pick holds its `SelKey` (`{Element, "door", -1, "end"}`, `{Element, "B1", -1, "edge 2"}`, `{Body, "tv"}`), the text a formula names it by (`end(door)`, `edge(B1, 2)`, a body's element qualified, `tv.e`), its frame and its position, a line's or an arc's ends and a round's centre as a formula names them (`A`, `end(door)`, `vertex(B1, 1)`), and a round's radius. The middle of a segment is a vertex, `mid(L1)`, only where the filter takes no Line, and of an arc only where it takes no Round, since a click on a curve lands near its middle; where the filter takes Body, a body's element gives its body, as a click selects it in world mode; the room's geometry is no pick. The pick is the canvas's hot key while the tool is active, and <kbd>Ctrl</kbd>, freehand for the snaps, picks the same. `ToolContext::pick_of(key)` reads a selected entry the same way (`Picker::of()`), hidden or not, and `picks_of(keys)` several from one `Picker`: a slot (`{Element, "leaf", -1, "to"}`) as the point it holds, a polyline or a box whole as nothing, since which edge is not said.

**`PickTool`** (`pick_tool.hpp`, beside `StateTool`) gives a constraint tool FreeCAD's `DrawSketchHandlerGenConstraint` rules. Its signatures are sequences of `PickFilter`s, prefix-free, and its `pick_filter()` is what extends one after the picks taken. A press on a pick that does so takes it; a pick taken already, or one `refuse()` refuses, is none, and a press on nothing takes nothing. A pick that completes a signature applies the tool: `propose()` says what it writes (the formula and its name's prefix, the `keys` written beside it, what a click does for the hint, the glyph and its anchor for the preview, a note for the report, or a refusal), refused when its formula is off its value and nothing it reads can move it there (`immovable()`, the Steps 9–10 ruling: "nothing horizontal(A, B) reads can move"; it settles a copy only when no pick reads a free value of its own, and a constraint that holds is added), and `apply()` makes the `SketchEdit`, by default that formula as a constraint named `prefix<k>` (`constraint_edit()`, through a `ShapeDraft`: one step "add horizontal h1", the constraint selected and revealed, the note in its report), committed through the context, a refusal in the notice; the picks then go and the tool waits for the next (continuous mode) or quits. While the pointer is over a pick that would complete a signature, `hint()` says what the click does ("Horizontal: a click adds horizontal(L1)") or why it would do nothing ("Horizontal: Impossible constraint: L1 is vertical (v1)"), and `preview()` shows its glyph at its anchor beside the picks taken, which it draws in the `Preview` role; a proposal is worked out once per pick under the pointer, not per move. <kbd>M</kbd> changes the method and keeps the picks (`on_method_changed()`), so that Point on object's `on_segment()` can be chosen before the last pick; <kbd>Esc</kbd> and a right click drop the picks, <kbd>Backspace</kbd> drops the last, and a document change drops them all, since a name they hold may now name another element. Started on a selection that holds sketch elements or bodies (`on_start()`), it reads them with `pick_of()`, in their order or else the first order that fits: a whole signature applies at once, and the tool quits; a signature's prefix becomes its first picks. A selection no signature takes, a selection of anything else (the constraint the last commit selected), and the selection a tool's commit made (`App::selection_from_tool()`, `ToolContext::selection_from_tool()`: a box drawn, then Fix) start it tool first (the Steps 9–10 ruling), the notice saying why `refuse()` refused a pick of it ("Fix: end(door) is derived from door: it has nothing of its own to fix"). The status bar names a selected part as a formula does (`selection_text()`: `end(door)`, a slot `L1 (to)`). A tool whose signatures need not be prefix-free completes by a placement instead (`PickTool::Completion::Place`, Smart Dimension): a pick that completes a signature is taken and waits, and so does a selection that completes one at the start; a left press that takes no pick (on nothing, on a pick taken already, refused, or that no signature goes on with) while the picks complete a signature calls `place()`, where the tool commits and drops the picks itself (`forget()`, then `committed()`, which quits it out of continuous mode). `on_picks_changed()` hears every change of the picks, from which `set_methods()` gives the methods <kbd>M</kbd> cycles for them, the first chosen; `taken_at_pointer()` is the pick a press would take; a `refuse()` with an empty reason refuses a pick silently, the hint then saying what the picks taken wait for, as over nothing.

**The constraint tools** (`constraint_tools.hpp`) are the `PickTool`s of plan 4.6 but Smart Dimension: `CoincidentTool` ({V, V}, {C, C}), `PointOnObjectTool` ({V, E or C}, {E or C, V}; methods `on_line()` and `on_segment()`), `DirectionTool` (Horizontal, Vertical: {E}, {V, V}), `AngleTool` (Parallel, Perpendicular: {E, E}), `TangentTool` ({E, C}, {C, E}, {C, C}, {V, E or C, E or C}), `EqualTool` ({E, E}, {C, C}), `SymmetricTool` ({V, V, E or V}) and `FixTool` ({V}, {C}, {Body}). Each reads the side or the orientation it writes from the picks' positions: `parallel(L1, L2, s)` with the sign of the dot product of their directions, `perpendicular()` with that of the cross product, `tangent(S, K, side)` with the side of S the centre is on, external or internal tangency of two circles by the nearer, `tangent_at(X, Y, P, s)` with the sign of the dot product of the tangents at P, a segment's from its first end, a round's counter-clockwise. Coincident follows `coincidence()` (`sketch_edits.hpp`), the rule the Arc tool's start shares: it merges two point elements of one frame (`merge_points()`), merges a point element into a derived point of its frame unless it is fixed (`merge_into()`: "the point becomes the reference"), refusing in its hint a derived point drawn from the point (`drawn_from()`), writes `coincident()` for two derived points or a fixed one (`co<k>`) and pins two frames (`pin<k>`); {C, C} applies the same rules to the centres. Tangent finds where two curves meet with `lies_on()`: an end of one that is an end of the other or that a constraint puts on it (`on`, `on_line`, `on_segment`, `coincident` with an end). Horizontal and Vertical refuse a line that has the other, found by `direction_constraints()` among the constraints of the line through the same two points, or by construction as an edge of a box of the world or two of its corners an edge apart, and the same one again; on the elements of one body they note that a world direction fixes its angle, unless a dry rank test finds that angle held already (a fixed pose, `angle(tv) == -90deg`). Parallel and Perpendicular refuse two edges of boxes of the world, and Equal two opposite sides of one, which hold or fail by construction and would fold away unreported. Fix refuses a derived point as a pick and an element fixed already, and applies `fix_sketch()`; on a circle or an arc whose centre is a free point element of its frame it fixes that point too, one step "fix K1 and its centre M" (the Steps 9–10 ruling). `provide_constraint_tools()` plugs them in, from App's constructor, Smart Dimension too.

**Smart Dimension** (`SmartDimensionTool`, `dimension_tool.hpp`, `tool.dimension`) is a `PickTool` that completes by a placement, with the signatures {V, V}, {V, E}, {E, V}, {E}, {E, E}, {C} and {C, C}. What it measures follows the picks (`measure()`): `dist(A, B)`; `len(L1)`; `line_dist(P, L1, s)`, s the side P is on; `angle(L1, L2)`, its arguments in the order that makes it positive, each line read away from an end the two share (FreeCAD's calculateAngle, so that a corner measures its inside: `angle(S2, S1, -1)` for sides drawn head to tail, the plain form when both start or both end there, its arc and its label's bisector in that sector; lines that share no end are read as drawn), or for two parallel lines the distance between them, `line_dist(<L2's first end>, L1, s)`; `radius(K1)`; `dist()` of two centres. Its methods follow them too (`set_methods()`): two points and a line have "by the label" first, where the label's place chooses the distance, Distance X (`B.x - A.x`, the right one first, so that the value is positive) or Distance Y, a level or plumb pair keeping the distance; then each of these chosen, and for a line its signed `angle(L1)`. The click that places the label (`place()`) tries the dimension at its exact measured value (`Measure::exact()`, `ShapeDraft::dimension()`'s `tried`: rounded, it would be off a drawing its constraints determine, a conflict where it is dependent), once, through `ShapeDraft::dimension()` and `edit()`, the rank test and `ToolOptions::dependent` of the creation tools' typed values (open question Q3), and writes it at the value the editor shows (`Measure::formula()`, 4 decimals of a metre, 2 of a degree), which the commit's settle reaches; one the rank test found dependent at the drawing and that stays driving all the same (an accidental configuration, `DependentDimension::Driving`; `ShapeDraft::Drafted::drawn`), or one no rank speaks of (its component above `sync_columns`; `Drafted::unranked`, `Tried::unranked`), keeps its exact value, to 12 significant digits, which the rounding would make conflict where the drawing cannot follow it. A dimension made a reference is committed at once, its report in the notice, and no editor opens; any other is held with the `SketchEdit` built for it, and the editor opens on the field contract below: the tool's one field, `value`, which `fields()` gives while the dimension is held, opened by `ToolContext::open_field("value", text, true)`, its text selected. `on_field()` (<kbd>Enter</kbd>, <kbd>Tab</kbd>, a press after a text typed) writes the text typed as the constant (`evaluate()`: a bare number is metres, or degrees in an angle), refusing a magnitude typed negative or zero and an angle between two lines past 180°, the angle of one line being signed, and the seed applied as it is like `on_field_closed()` (<kbd>Esc</kbd>, a press with nothing typed), which writes the value shown, or the exact one above; <kbd>Tab</kbd> on the untouched editor keeps it (`field_key()` gives `None`); a right click (`escape()`) and a document change under it drop it. Either commit is the one batch built at the click, one undo step ("add distance d1", "add angle a1", "add radius r1"), the dimension selected. The value typed is not tried again: one far from the drawing is reached by the continuation of `Document::apply()` (`SettleOptions::previous`), and one the others contradict is left out by the commit's settle as conflicting (open question Q4). The label's place is written as `"label": {"offset": [u, v]}` in the kind's axes (`dimension_label.hpp`, whose `dimension_label()` gives a stored dimension's from its formula and the scene's picks, the same as the tool's, which a test checks for every signature; plan 4.7: a linear dimension's from the middle of the two points measured, along the measured direction and its left normal; an angle's from the vertex, along the bisector; a radius's from the centre, along the x axis for a circle and through the middle of an arc), unless the click is within 3 pixels of where `default_label_offset()` puts a label that has none: 24 pixels across a linear dimension, 48 along an angle's bisector, 24 beyond a radius's rim, at the view's scale.

Every tool of plan 4.3 is a `ToolSpec` of `tool_specs()`, registered as an action `tool.*` with its chord (Shift and a letter create, a letter alone constrains), Canvas scope and `exact_mods`, whether implemented or not: `ToolHost::provide(id, factory)` plugs an implementation in, and until then the action is disabled, its `tip` saying it is not available yet. A second run of the active tool's action quits it, unless the tool is a constraint tool and the selection holds sketch entries that no tool commit made: it starts again on them, so that Smart Dimension select-first twice measures the second selection. `tool.finish` (<kbd>Enter</kbd>), `tool.back` (<kbd>Backspace</kbd>), `tool.field` (<kbd>Tab</kbd>, the current state's first unset field opened empty, positional ones included) and `tool.method` (<kbd>M</kbd>) are Global actions with `exact_mods`, enabled only while a tool is active and either no panel has the keyboard or the pointer is over the canvas (`CanvasController::hovered()`, the last update's): a list clicked during a shape keeps the keyboard, and the tool's keys follow the pointer back over the canvas, as its chords and the typed digits do. `App::toolbar()` lists the tools' actions in the groups Create, Constrain and Body, then the Options toggles `tool.auto_constraints`, `tool.helper` and `tool.grid_snap`, a group whose `Menu::options` says that a toolbar shows its entries as check boxes.

`ToolHost` compares the document's instance, path, compile and restore generations at each call into the tool and at `App::tick()`: a presenter edits the document without any action, and a slot must not change the App, so the comparison, not a hook, tells the tool (`on_document_changed()`). A reload of the document's file is such a change, and the tool stays; another document, or one that no longer compiles, quits it (a tool needs a drawing to aim at: its action is disabled until the document compiles, `ToolHost::drawable()`); the tool's own commits are no change under it.

**The value fields.** `ToolHost` keeps the field being typed in (`editing()`), with `FormulaDraft`'s contract, so that a retained toolkit can bind it:

- `take_field_focus()`, once: the field to give the keyboard to;
- `take_text_update()`, once: the text and caret the host set itself (a seed, a revert, a refused text kept), which the field puts in its own buffer, also after a focus that selected the whole text, and whether that text is to be selected (`select`, a field a tool opened with its measured value, so that the first key typed replaces it; the characters `typed()` takes before the view's field has the keyboard replace it the same way, or the view would show `0.35` for `5` typed fast over `0.3`);
- `set_field_text(id, text)`: the view's edit; a field that was not open opens with it;
- `field_key(id, key)`: <kbd>Enter</kbd> applies (`Applied`, or `Refused` with `ValueField::refusal`, the field keeping the keyboard), <kbd>Esc</kbd> reverts that field only (`Reverted`), <kbd>Tab</kbd> applies a text typed and opens the current state's next field empty, wrapping around (`Moved`), or nothing once the text applied completes the state (`Applied`). A digit, `=` and <kbd>Tab</kbd> open the current state's fields only, as FreeCAD's on-view parameters belong to it: a field of a state placed already (`placed`, A's x and y once B is next) is shown, and opened by none of them. In a view whose closed fields are widgets too, a click may give one the keyboard with no call to the host: it is not open until its first edit, and its keys go to `field_key()` all the same, Esc giving `Reverted`, so that the view takes the keyboard from it, and Tab `Moved`. The ImGui view draws a closed field as a frame with its text, which no click hits.

**Typed characters.** `CanvasController::typed(text)` gives `ToolHost` what is typed over the canvas while no text field has the keyboard: a digit, `-`, `.` or `(` opens the current state's first unset dimensional field and seeds it, `=` opens its first unset field empty, and letters seed nothing: their keys ran the registry's actions, so that <kbd>T</kbd> starts Tangent. A field is open from its seed on, before the view gives it the keyboard (two frames later in ImGui). It takes every character typed until the view reports that its field has the keyboard (`ToolHost::field_focused(id)`: ImGui's on each frame its `InputText` is active and takes the text input, `WantTextInput`, which is from the frame after the one that activates it, wxWidgets' on `EVT_SET_FOCUS`; a reported edit counts too), so that `30cm` typed in a burst stays whole, and after that only a digit, `-`, `.` or `(`, which give it the keyboard back: a blank or a letter is left alone, so that <kbd>Space</kbd> + drag still pans over a text left in a field that lost the keyboard. While it waits for the keyboard, its letters' keys fire nothing (`KeyFocus::field`, above); once its view has had it, they fire again, a text left in it included. While it is open without the keyboard, its own keys act on it: `tool.finish` applies it as <kbd>Enter</kbd> in it would, `tool.field` moves on as <kbd>Tab</kbd> would, `tool.back` erases its last character and `app.escape` closes it. A text left in a field that lost the keyboard applies before the next press, which a refused one keeps from placing anything, and is the first step of <kbd>Esc</kbd>; a field with nothing typed into it (empty, or its own text) closes at the press unapplied, since the tool refuses an empty text and the press would place nothing. A right click takes such a text with the shape, in one step (`ToolHost::right_click()`): plan 4.3's chain from step 3.

### Change notifications

`Document`, `Selection`, `CanvasController`, `SketchSession` and each list presenter emit a `Changes` bit set once per public call that changed something; `App::changed()` forwards all but the lists' and adds `Solver` from `tick()`, `Scene` when `scene()` computed the scene again, `Panels` when a panel opens or closes, `Hover` when the hot key changes, `Visibility` when an eye of a name does and `Player` when a sweep player plays or pauses (`toggle_play()`). `Sketch` comes from the Document when the sketch model or the diagnosis changes, and from the `SketchSession` when a drag's live values, its end or the monitored statuses do, or a diagnosis fails (the sketch message then says so). The notice of the last sketch edit (`App::notice()`: a refusal in `Tone::Warn`, or what an edit deleted with it) is logged when it is set, so `Log` comes with it; it lasts while the selection and the compile generation stay, so a retained status bar reads `segments()` again on `Log`, `Selection` and `Content`. `Tool` comes from `ToolHost`, once per public call that changed what a view shows of the tools: the active tool, its hint, method, state, fields or preview, the field being typed in, a request for that field's keyboard or text (raised again too: a refused <kbd>Enter</kbd> asks the keyboard back), the options; a move that changes none of these emits nothing. `Structure` also comes when the document gains or loses its sketch section (a tool's first shape, its undo), which changes the lists' groups, columns and filters. A list's `Filters` is on its own `changed()` only, so that a filter of one list resets no other. A retained toolkit subscribes and refreshes what the bits name. An immediate-mode front-end redraws every frame and needs no subscription. A slot must not change the App synchronously.

### Presenters

Each panel has a presenter that holds what it shows and does, without widgets:

- **Rows** are keyed by the typed `SelKey`. A list panel's presenter is a `ListPresenter` ([Lists and Properties](#lists-and-properties)). An edit recompiles the document at once: a view that reads several values in a frame reads them after the edit, and stops drawing what read paths before a rename or an erase.
- **Statuses** are a text, a `Tone` (Ok, Active, Bad, Warn, Dim, Neutral, Normal) and a tooltip. The front-end's theme turns a tone into a colour.
- **Texts** are the presenter's: numbers, units, counts and messages are strings when they reach the view, and so are the labels, tooltips, titles and buttons of its widgets, such as `SolverPresenter::kSettings` or `PathDialog::title()`. Views keep widget IDs and the printf formats that widgets such as sliders take.
- **State between frames** that is not the document lives in the presenter: the text of a field being edited (`FieldDrafts`), the value of a sheet's drag while it is held, the bounds a criterion parked when its role changed, the rename editor, the lists' filters and the entries Associated starts from, the Pareto study's choices, the margins' normalise flag. The drafts and the rename editor are `PanelHost`'s, which every panel shares and which drops them when the Document reports `Instance` or `Structure`: a path kept across it may name another entry.
- **Operations** change the document: `set_enabled`, `set_role`, `set_sampling`, `edit_value`, `rename`, `erase`, `add`. Those of the lists and of Properties are keyed by a row's id or an entry's key and find their entry again on each call ([Lists and Properties](#lists-and-properties)).

A row or a sheet lists its text fields as `Field`s: the JSON path and the `FieldKind` that says which JSON value Enter stores (a sweep's `samples` stays an integer, a display label stays a string). A `Number` field refuses any text that is not a number literal, keeps the draft pending and says why in `Draft::refusal`. A view draws each between `FieldDrafts::begin()` and `end()`: `begin()` returns the draft the text widget edits in place; `end()` receives whether the widget is active and whether Enter applies the text, and applies it. `FieldDrafts::enter_applies()` tells whether Enter, with Ctrl or not, applies: in a `MultilineText` field Enter types a new line, and only Ctrl+Enter applies. An error at a key that has no editor gets a raw JSON field under its entry: a sheet names the keys its editors own (`DetailSheet::owned()`) and passes them to `FieldDrafts::diagnostics()`. A draft stays pending, with its text, until <kbd>Enter</kbd> applies it, whether its field loses the keyboard or stops being drawn; `FieldDrafts::pending()` lists them, the oldest first, for the status bar.

With a sketch, Elements lists a Sketch group first: the world's elements, then each body as a row whose `children()` are its members, with a Helper column (a `Check`, one step); its values are a drag's live ones while it runs (`sketch_values()`), and its states come from the diagnosis (`element_state()`, `body_state()`: "free", greyed, until one lists the element; greyed while `sketch_stale()`, as the sketch message is). Constraints puts each constraint under Geometry or Design by `ConstraintInfo::role`, its equality group's, which a disabled constraint or a reference dimension has too, read while the document does not compile from the last good model, matched as its statuses are (`entry_index()`); a Geometry row's status is what the sketch solver says of it (`sketch_standings()`: satisfied, redundant, conflicting, malformed, "reference = v"), a Design row's is live from `SketchSession::monitored()` during a drag. Its Eye column is the glyph's of a constraint whose kind has one. A file without a sketch keeps the single group "Design requirements", and its sketch columns stay empty.

A list that reads as a table implements `TablePresenter`: headers, a row count, rows of typed `Cell`s read on demand, and `activate()` and `choose()` for clicks. `SolutionsTable` is one. The ImGui front-end draws any of them with `table_view()`. It addresses rows by index, which only a list rebuilt with each result can do; the panels' lists use `ListPresenter`, whose cell kinds include `Cell`'s, so until the Solutions table moves onto it a front-end has two table adapters.

### Lists and Properties

A list panel's presenter is a `ListPresenter`, which a retained toolkit can back with one generic model (a `wxDataViewModel`) and the ImGui front-end draws with `list_view()`:

- **Rows by id.** A row is a `RowId`: the entry's `SelKey` and an ordinal among the rows of that key (names repeat while a document does not compile). A group header is a `RowId` with a `group` and an empty key (`header_row()`): it names no entry, has no path, and is never selected, hot, renamed or toggled. `children(parent)` gives the rows the filters let through, in order, the top level for none, also under a collapsed row: `expanded(id)` and `set_expanded(id, open)` keep the tree's expanders, every row open until collapsed, which emits nothing. `Panels::shows()` and Up and Down (`Panels::step()`) take only the rows under expanded ones, and a reveal or an Add (`Panels::unhide()`) clears the filters that hide its row and expands the rows above it; `row(id)` reads one, with its `parent`, `depth`, `expandable`, the entry's path now (empty for a header or an entry of an included file), `dim` (a use through lets), a `tooltip`, and one `ListCell` per column for an entry, or the `label` of a header, which spans the row and has no cells. A row keeps no index: `row()` resolves the id against the document each time and gives nullopt for an id that names nothing now, so a toolkit that reads values lazily never reads another entry's.
- **Rows are summaries.** A cell is text with a `Tone` and a tooltip, the entry's name, or a toggle: a `Check` (enabled, released) or an `Eye`, with `on`. Each `Column` has the `kind` of its cells in an entry's row: a cell is of that kind or `Empty`, or `Text` in the `Name` column for a row without a name to rename (an anonymous display item), so that a toolkit picks one renderer per column before any row exists. `column_shown(i)` says whether a column is drawn now: a column only a sketch fills (Elements' Helper, Constraints' Eye) is hidden in a document without one, which shows as it did before sketches; the columns and their indices stay, so `toggle()` and `activate()` take the same column either way. The editors are in Properties. A column that shows a value at the sweep position reads `App::scene_now()`, the scene the frame computed: `scene(false)` would start the fine check in the middle of a drag. That value changes when the frame computes the scene, after the change of x or of a sweep that `App::changed()` reported: `scene()` emits `Scene` then. `footer()` gives lines under the rows, such as the size of the problem in Ranges, read again with the rows.
- **Operations** are keyed by the row, and do nothing for a stale id or a header: `toggle(id, column)` flips a toggle cell; `activate(id, column)` says what a double click on a cell, or <kbd>Enter</kbd> on the row (no column), asks for, an `Intent` (`Rename` on a name with a path, `OpenFormula` elsewhere in the row of a let, a constraint or a criterion, `FocusProperties`, `None`), which `Panels::activate(panel, id, column)` carries out, giving the keyboard to the sheet's first field, or opening the [formula pop-up](#the-formula-pop-up) on the entry; `PanelHost::click()` selects. The toolbar's actions are `toolbar()`, and the App's actions act on the selection.
- **Filters** are `filters()`: checkboxes, choices and texts, with their values. `set_filter(i, value)` and `clear_filters()` emit `Filters` on the list's own `changed()`, which `App::changed()` does not carry: a retained toolkit subscribes to each list's signal and resets that list alone, since a row's ordinal counts the rows the filters let through, so an id may now name another entry. `clear_filters()` gives each its default, which hides none of the entries the list is the home panel of: `App::reveal()` calls it on a home list that hides the revealed entry, and so does an Add. The Associated filter of Constraints and Criteria shows the entries that use what was selected last outside them (`associated()`): its rows follow the selection, so `resets_on()` has `Selection` while it is on. The Violated filter reads its verdicts from `App::scene_now()`, so `resets_on()` has `Scene` while it is on. A filter's tooltip may name the selection, as Associated's names the entries it starts from: a toolkit reads `filters()` again on a reset and on `Selection`.
- **The invalidation contract** is `resets_on()`. On `App::changed()`, and on `Filters` from the list's own `changed()`, a retained toolkit:

| Change | It does |
| --- | --- |
| a bit of `resets_on()` (`Instance`, `Structure`, `Selection` while Associated is on, `Scene` while Violated is on), or `Filters` from the list's own `changed()` | drops its ids and reads `children()` again (`Cleared()`), and `filters()` |
| `Content` otherwise | compares `children()` with its ids, under every parent, and adds and removes rows by `RowId`: an appended entry or an erased object key moves no path, so `Structure` is not set (`ItemAdded()`, `ItemDeleted()`). A row may move to another parent with its id (a constraint whose edit takes it between Geometry and Design): it removes every row that left its parent, under every parent, before it adds any (`ItemDeleted()` under the old parent, then `ItemAdded()` under the new one) |
| `Content`, `Model`, `Values`, `Sweep`, `Visibility`, `Solver`, `Scene`, `Sketch` | reads `row()` again for the rows it shows (`ItemChanged()`), `footer()` and `column_shown()` |
| `Selection`, `Hover` | no row changes: it syncs its own selection, tints the hot row, and reads `filters()` again on `Selection` |
| `Tool` | nothing: no list shows a tool |

`tests/app/test_list_adapter.cpp` holds such an adapter, run on every kind of change, over every list panel and over a list with a header, toggles, dim rows, filters and intents, and over a sketch's bodies, the rows under them, their Helper toggles and the glyphs' eyes: its cache must equal a fresh read after each one.

**Properties** shows the sheet of the selection, `PropertiesPresenter::sheet()`, a `DetailSheet`: a title, then `DetailItem`s, then the diagnostics of the entry. A sheet is built by the `SheetBuilder` of the entry's kind (`EntryKind`: a param, a design point or scalar, a sweep, a let, a constraint, a criterion, a display item, a geometry entry, a sketch element, a body), whichever list shows the entry, so an entry listed twice has one sheet and each key one editor. A display item that draws a name has no row: its style is a section of the name's sheet (`add_drawing()`), a design point's or a let's. The formula of a let, a constraint or a criterion is a read-only `Value` with the id `formula`, whose `field` names the key it shows, followed by the `Button` `edit_formula`, which opens the [formula pop-up](#the-formula-pop-up) on the entry: one editor per key. Each item has an `id`, the same in every sheet of its kind, and a kind:

| Item | Shows | Edited by |
| --- | --- | --- |
| `Name` | the name in `text` | `set(key, "name", text)`: renames it and every use, one step |
| `Field` | a text field, its key's text in `text`, `refusal` when the last text was refused | `set(key, id, text)`, as <kbd>Enter</kbd> would; a refused text leaves no unapplied draft: it stays in the toolkit's editor, its reason in `refusal` until the field's next `set()`. An immediate-mode view edits it through `FieldDrafts` |
| `Value`, `Note` | read-only text, a hint; a `Value` with a `field` shows a key another editor edits (a formula) | |
| `Checkbox` | `value`, a bool | `set(key, id, bool)` |
| `Choice` | `value`, the index in `choices`, -1 for none of them; `text`, what the closed choice shows, the document's text for none of them | `set(key, id, index)` |
| `Drag` | `value`, one number or two, or an `int` for a whole number, with `min`, `max`, `speed` and `unit` | `begin_drag`, `update_drag`, `end_drag`: one undo step; or `set()`, which writes what a drag to the same value writes: a sketch value the solver moves is typed as one frame of its `SketchSession` drag, under the drag's label. A value typed into the field goes as one `update_drag` when the field is left (Enter, Tab, a click elsewhere), none at Esc, never one per keystroke: typing 120 into an arc's end would otherwise drag the sketch through 1 and 12 |
| `Slider` | `value`, a number between `min` and `max` | the same |
| `Colour` | `value`, an `Rgba` | `set()`, or a drag |
| `Button` | its caption in `label` | `press(key, id)` |
| `Link` | `text`, naming `target`, a `SelKey`; plain text without one (a slot that holds a constant) | `press(key, id)`: selects the target alone and reveals it (`App::reveal()`), in every builder |
| `Section` | a heading in `label`, over the items up to the next one | |

Each operation goes through `PropertiesPresenter` (`set`, `press`, `begin_drag`, `update_drag`, `end_drag`) to the builder of the key's kind, which builds the sheet of the key again: a key that names nothing now, an id the sheet no longer has, a read-only item and a value of another type change nothing and give false. A drag shows its values in `sheet()` while it is held and writes the last one at `end_drag()`, unless its builder moves the document while it is held (a released point in a Document gesture); `finish_drag()` ends a drag whose release the toolkit lost, in every builder; `begin_drag()` first ends a drag left open in another builder. `DetailSheet::owned()` lists the keys of its fields, checkboxes, choices, drags, sliders and colours, and those its values show for another editor, which `FieldDrafts::diagnostics()` takes: an error at any other key of the entry gets a raw JSON field.

A retained property sheet follows this contract, which `tests/app/test_sheet_adapter.cpp` checks with a fake one:

| Change | It does |
| --- | --- |
| `Selection`, `Instance`, `Structure` | builds its properties again from `sheet()` |
| `Content`, `Model`, `Values`, `Sweep`, `Visibility`, `Solver`, `Scene`, `Player`, `Sketch` | reads `sheet()` again: when its items have the same ids in the same order, it sets their values in place, and an editor in use keeps its state; else it builds them again |
| after one of its own operations | reads `sheet()` back: a drag held in the builder changes no document, so no change is emitted |
| `Tool` | nothing |

The Document panel is a sheet of no entry: `DocumentPresenter::sheet()` and its `set(item, value)` and `press(item)`, the same items and the same contract.

`PanelHost` (in `App::panels()`) holds what the panels share: the drafts, the name editor, which is open on one entry in one panel at a time (`RenameEditor::editing(entry, panel)`), and which reveal each panel took. The text being typed in the name editor is the toolkit's: `PanelHost::rename(key, text)` commits it and `cancel_rename()` closes the editor; a refused name keeps the editor open, with `RenameEditor::refusal(entry)`. Three requests reach a panel, each taken by the view that draws its target:

- **Rename**: a double click on a name in a list (`Panels::activate()`) or in Properties (`PanelHost::open_rename(key, panel)`) opens the editor where it is; F2 asks the focused panel when it lists the entry (`App::set_focused_panel()`, which the front-end reports), else Properties, which comes to the front. An Add (`App::add_entry()`) selects and reveals its entry, then asks the focused list when it shows it, else the entry's home list, which comes to the front with the filters that hide the entry cleared. A constraint or criterion without a name is keyed by its place (`unnamed()`), so that it can be selected, shown in Properties and given a name. `PanelHost::take_rename_request(panel)` opens the editor when the request is that panel's. It lasts until taken, or until the selection is no longer that entry alone or a path moves.
- **Reveal**: `Selection::reveal()` bumps `reveal_generation()`; `PanelHost::take_reveal(panel, key)` is true once per panel and reveal, so every list that shows the row scrolls to it, also one shown later. `App::reveal()` also brings the home panel forward (`home_panel(doc, key)`, by the entry's kind), then Properties, whose first field takes the keyboard, none for a let, a constraint or a criterion, which are edited for their formula, in the pop-up.
- **Field focus**: `App::request_field_focus(path)` (the status bar's unapplied edits, <kbd>Enter</kbd> on a row, a double click on the canvas, a problem of Messages: `MessagesPresenter::activate(i)`, which reveals the entry, then asks for the field of the problem's key when the sheet has one, or opens the formula pop-up for a problem of a formula); `take_field_focus(path)` is true once, for the view that draws that field. It goes stale when a path moves. The ImGui view takes it only once the field's window has the focus, which the panel focus request gives it: a field that took the keyboard first would focus its window before the panels asked for ahead of it.

### The formula pop-up

`FormulaDraft` (`App::formula()`) is the pop-up without its widgets. `add_constraint()` (pre-filled by `constraint_prefill()`, or with the `Prefill` it is given), `add_criterion()`, `add_quantity()` (the actions `formula.add_*`) and `edit(key)` (`formula.edit`, `OpenFormula`, the sheets' Edit formula, a problem of a formula in Messages) open it; on a selection of the sketch's elements, the actions pre-fill it with `sketch_prefills()` of the entries as a constraint tool picks them (`Picker::of()`, in the last scene): **Add constraint** with `dist(A, B) >= `, `len(L1) <= ` or `clearance(X, Y) >= `, and `formula.add_range`, `formula.add_order_x` and `formula.add_order_y` with the range ` <= dist(A, B) <= ` and the orders `A.x > B.x` and `A.y > B.y` as drawn, `>=` for two points level or plumb at 4 decimals, where `>` would be violated as drawn (plan 4.6's Bounds, the user's D4 examples), each enabled only where it applies, so that the context menu of a file without a sketch is unchanged; `take_open_request()` tells the front-end once, and the front-end closes its window once `is_open()` turns false. It holds:

- **The formula** as text and a caret, which the front-end reports with `set_text()` after an edit and `set_caret()` after a move. `take_text_update()` gives, once, the text and caret the draft set itself (an opening, `accept()`, `insert()`), for the field: a toolkit's field keeps its own buffer while it has the keyboard (ImGui's), or takes `ChangeValue()` and `SetInsertionPoint()` (wxWidgets), which count characters where `caret()` and `replaced()` count bytes.
- **The candidates**, `candidates()`, the names the identifier at the caret completes to, with the bytes `replaced()` they replace, shown while `list_shown()`: a front-end lists them where it likes, inline under the field (ImGui's modal: a window over a modal would be dimmed and blocked), or in a list of its own under the field, which leaves the keyboard in the field. A toolkit's completer cannot show them: `wxTextEntry::AutoComplete()` completes the whole text rather than the name at the caret, its `wxTextCompleter` runs off the main thread on MSW, and its popup takes Up, Down, Enter and Esc, which `key()` must see. `accept(i)` takes one; `insert(key)` puts an entry's name at the caret, for a pop-up that is not modal.
- **The keys** of the field go to `key()`, which says what it did (`Outcome`): Up and Down move the highlight; Enter accepts it, or commits when the highlighted name is already typed in full; Esc hides the list, then cancels; Tab hides it and moves on. A field that handles Esc itself must not see it: ImGui's reverts its text first, so the view claims Esc with `Shortcut(ImGuiKey_Escape, ImGuiInputFlags_RouteGlobal | ImGuiInputFlags_RouteOverActive)`.
- **The other fields** as sheet items, `fields()`, edited with `set(id, value)`: the name, the quantifier, Enabled for a new entry, and a criterion's role, bounds and unit.
- **The check**, `check()`: compiled again into a copy of the instance when the text, a field or the document changed, evaluated again at the document's x and sweep positions when `Values` or `Sweep` changed, and read as it is otherwise, so a view may read it every frame. A slot of `App::changed()` only marks it due.
- **The commit**, `commit()`, one `EditBatch`, or a `refusal()`; a new entry is selected and revealed (`App::show_added()`). Another instance closes the draft, and so does a change of paths while it edits an entry, which it keeps by its path.

The Panel scope's actions act on the focused list: <kbd>Enter</kbd> (`list.activate`) activates the row, <kbd>Up</kbd> and <kbd>Down</kbd> (`list.previous`, `list.next`) move the selection.

#### Binding wxWidgets (a sketch)

No wxWidgets front-end exists, and nothing here was tried against wxWidgets: it maps the contracts above onto the classes a port would likely use.

- **`wxDataViewModel`**, one generic model over any `ListPresenter`: intern each `RowId` as a node whose address is the `wxDataViewItem`, dropped on `Cleared()` and `ItemDeleted()`. `GetChildren()` is `children()`, `IsContainer()` is `expandable`, `GetParent()` is `parent`. Each column gets its renderer when it is added, from `Column::kind`, and `SetHidden(!column_shown(i))` on a reset and with the rows: a `wxDataViewToggleRenderer` for a `Check`, and for an `Eye` a custom renderer that draws an eye, since a tick would read as "enabled", each activation calling `toggle(id, column)`, else a text renderer, in editable mode for the `Name` column, which is also the expander column (`SetExpanderColumn()`). `HasValue()` (wxWidgets 3.1.4 or later) is false for an `Empty` cell and, in a header, true in the `Name` column alone, where `GetValue()` gives its `label`; elsewhere `GetValue()` is the cell's text, or its `on` for a toggle; `EVT_DATAVIEW_ITEM_START_EDITING` vetoes an edit outside a `Name` cell or in a row without a path; `GetAttr()` gives the tone's colour, the faded colour of a `dim` row and the hot row's tint. `EVT_DATAVIEW_ITEM_ACTIVATED` calls `Panels::activate(panel, id, column)` and opens the name's in-place editor on `Rename`; `EVT_DATAVIEW_ITEM_EDITING_DONE` on the name calls `PanelHost::rename(key, text)` and vetoes the edit when it returns false, showing `refusal()`; a cancelled edit calls `cancel_rename()`. The filters are controls above the list (`wxCheckBox`, `wxChoice`, `wxSearchCtrl`) calling `set_filter()`, and the footer static texts under it. Selection, the context menu and hover go to `Selection::assign()`, `App::context_click()` and `set_hot()`, and a reveal to `EnsureVisible()`, which opens the rows above it as `unhide()` did. `EVT_DATAVIEW_ITEM_EXPANDED` and `EVT_DATAVIEW_ITEM_COLLAPSED` call `set_expanded()`, and after a `Cleared()` the control expands the rows `expanded()` names, since it rebuilds them closed.
- **A tool and its value field**: the toolbar's `wxAuiToolBar` check tools run their actions on `EVT_TOOL` (`actions().find("tool.horizontal")->run()`, then `app.sync()`), with `EVT_UPDATE_UI` reading `is_enabled()` and `is_checked()`. The canvas, a `wxWindow` with `wxWANTS_CHARS`, takes the focus on `EVT_ENTER_WINDOW` and `EVT_LEFT_DOWN`; its mouse events become `PointerInput`s for `update()`, which fills `ToolEvent::pick` and feeds `ToolHost`; `EVT_KEY_DOWN` goes to `run_pressed()` in `App::key_focus(KeyScope::Canvas, ...)`, skipped when nothing ran, and `EVT_CHAR` to `typed()`; on `Tool` the status bar shows `tools().hint()` and the canvas refreshes, and on `Instance`, `Model` or `Sketch` the re-feed above runs. Smart Dimension's editor is one child `wxTextCtrl` (`wxTE_PROCESS_ENTER | wxTE_PROCESS_TAB`), moved to the field's anchor on `Tool` and `View`, shown while `editing()` names it: it takes `take_field_focus()` (`SetFocus()`) and `take_text_update()` (`ChangeValue()`, `SetInsertionPoint()`, `SelectAll()` when `select`), reports `EVT_SET_FOCUS` with `field_focused()`, `EVT_TEXT` with `set_field_text()`, and Enter, Esc and Tab with `field_key()`, giving the focus back to the canvas unless the outcome is `Refused` or `None`. Digits typed before its `SetFocus()` lands reach the canvas's `EVT_CHAR`, and `typed()` replaces the selected seed with them.
- **`wxPropertyGrid`**, one grid over `PropertiesPresenter::sheet()`, each property named by its item's `id`: a `Section` is a `wxPropertyCategory`, a `Name` or a `Field` a `wxStringProperty` (a `MultilineText` field a `wxLongStringProperty`), a `Value` a read-only `wxStringProperty`, a `Checkbox` a `wxBoolProperty` shown as a checkbox, a `Choice` a `wxEnumProperty` over `choices`, a `Drag` or a `Slider` a `wxFloatProperty` with `min` and `max` as attributes (a 2-D drag a parent with two children), a `Colour` a `wxColourProperty`, a `Button` a property with a button editor, a `Link` a read-only `wxStringProperty` whose button editor calls `press()`, and a `Note` the grid's description. `EVT_PG_CHANGED` calls `set(key, id, value)` with the property's new value, vetoing the change and showing `refusal` when it gives false; a spin or slider editor held by the mouse calls `begin_drag()`, `update_drag()` on each change and `end_drag()` on release; a button calls `press()`. `take_field_focus(path)` selects the property whose item edits `path` and starts its editor. The Document panel is a second grid over `DocumentPresenter::sheet()`, a `MultilineText` description included.

### Panels, layout and settings

`App` holds which panels are open (`panel_open()`): the front-end shows those, and reports a panel the user closed with `set_panel_open(id, false)`. View > Panels toggles them through the actions `view.panel.<key>`. Two requests are taken by the front-end after each input event, the way dialogs are: `take_panel_focus()`, raised by `focus_panel()` (a status bar link, `--tab`, a double click on the canvas through `App::reveal()`, F2 for Properties), brings a panel to the front: the requests come the oldest first, and the last one keeps the keyboard, so that a double click shows the entry's list and then puts the keyboard in Properties. `take_layout_reset()`, raised by View > Reset layout, asks for the default layout; App reopens every panel itself.

The layout belongs to the toolkit: the front-end saves it as a blob of its own format with `save_layout(key, version, blob)`, under a key of its own (`layout.imgui`; a wxWidgets front-end would use `layout.wxaui` for `wxAuiManager::SavePerspective()`), and asks `load_layout(key, version)` before showing anything. `version` is the version of its default layout, kept beside the blob under `<key>.version`, so that two front-ends sharing one `settings.json` keep their own layouts. It is bumped when that layout gains or loses a window: a layout saved by another version, or none, gives nullopt and every panel open, and the front-end builds its default layout.

`App` reads and writes these through the `SettingsStore` it is constructed with, beside its `SolverBackend`. The GUI passes a `FileSettingsStore` over `default_settings_dir()`; scripted runs and the tests keep the default `NullSettingsStore`, so they never depend on, nor change, the user's settings.

### Selection, hot key and eyes

The `Selection` holds `SelKey`s, by kind and name: a display item, which has no name, by its place in `display`. Two more keys follow the pointer and the eyes:

- **The hot key** is the entry under the pointer: the canvas's pick, else the row a list view reports with `App::set_hot(HotSource::List, key)`. The canvas outlines it, a list tints its row. `Hover` is emitted when the key changes, not on every move, so a view may report the hovered row on every frame or event, and nothing once no row is hovered.
- **The eyes** are stored with what they hide. An anonymous display item's is its `visible` key, an edit of the document. A name's (a design point, a geometry entry, a let, a sketch element, a body, whose eye hides its members too) is kept by `Visibility` in the settings, under `visibility.<absolute path of the file>`: not an undo step, and it outlasts undo, reload and the next start. A display item whose expression is just a name is that name's drawing (`display_keys()`): a pick on it selects the name, and it hides with the name. `eye_of()` and `set_eyes()` apply this rule.

A constraint's glyph has an eye of its own, kept beside the names' (`Visibility::glyph_hidden()`): a constraint may share its name with a point.

An edit made outside `App`'s own actions that renames an entry or erases a display item must be followed by `App::entry_renamed(key, name)` or `App::display_erased()`, which bring the selection, the eyes and the hot key along (a body's rename moves every `tv.*` key and eye, through `renamed_prefix()`; a member takes its new name within its body or qualified); `sync()` would otherwise drop the entry from the selection. `sync()` itself follows the renames an undo or a redo took back or made again (`Document::restored_renames()`).

### Dialogs

A dialog presenter raises an open request when the application has a question; the front-end takes it once with `take_open_request()`, shows its dialog and calls the answer back (`submit()`, `save()`, `confirm()`, `cancel()`). Before Save As replaces another file, the ImGui dialog asks itself: the user presses Save a second time. A native save dialog that has already asked answers with `submit(PathDialog::Replace::Confirmed)`.

### The canvas

`CanvasController` takes one `PointerInput` per update (an ImGui frame, a wx mouse event): position, motion, wheel, hover, the button pressed with its click count (2 for a double click) and whether it is held, the modifiers, whether Space is down and whether a text field has the keyboard. It picks, selects, draws selection boxes, drags, pans, zooms and fits, and sets the hot key from its pick. `pick()` takes, in order, a handle, a point, an edge within 4 pixels, then the inside of a shape drawn filled; what the View menu or an eye hides is never picked, boxed or fitted. A right click calls `App::context_click()`, and a double click `App::reveal()`. The sketch is picked between the lets and the geometry: its point elements and arc ends within 7 pixels, then its edges, circles and exact arc rims within 4 pixels; an element of a body is picked as the body (`{Body, "tv"}`), which a box selects once all its elements are inside. A left press on an element of the world drags it through a `SketchSession` drag of the gesture its `Pick::Part` names (`drag_point`, `drag_edge` for both ends of an edge, `drag_circle_edge` and `drag_arc_edge` by the rim, `drag_arc_end`), begun once the press is a drag: it writes nothing while held and applies one step at the release; a fixed point draws a box, as a fixed handle does. While a tool is active, the left button's press, the moves and the release go to it (`ToolHost::event()`) with what the pointer snaps to, which is the hot key, a right click is the Esc chain from the tool, and the hover text is none; the middle button, a right drag, Space and the wheel pan and zoom as without one. Open fits the sketch's `extent` first (`FitRequest::Extent`), the design without one. `build_canvas_display()` then fills a `DisplayList` with the canvas in drawing order: world-space paths and circles, screen-space lines, rectangles, markers and texts, each with a semantic `Role` (`Selected` and `Hot` outline entries, `SelectionBox` is the box being drawn). A front-end replays it on its `Painter` and gives the builder a `TextMeasurer` for its font, which places the labels. A sketch's elements are drawn from the scene's values (`Scene::sketch`, and `Scene::arcs` for an exact arc, tessellated to 0.25 px at the view's zoom rather than drawn as the polyline the optimiser reads), in the roles `Element`, `ElementHelper` and `ElementFixed`; during a sketch drag the front-end passes `SketchSession::scene()` as `live`, whose elements, lets and display items are drawn instead. Without a design-mode model, the elements of `Document::background()` are drawn, so an error elsewhere hides no drawing. The fits take the elements in as they take the design: Fit design and Fit all fit them, Fit selection the selected ones.

### Time

`App::tick(dt)` advances the sweep players and polls the solver job, copying its new results before it emits `Solver`, then lets the `SketchSession` cancel a drag of an older sketch generation, start or poll the diagnosis worker, and bring the monitored statuses up to date; `App::busy()` says whether it still has work, a sketch diagnosis waiting or running and monitored statuses older than the sketch or `x` included. The ImGui loop calls `tick` every frame. An event-driven toolkit calls it from a timer while `busy()` is true, and checks `busy()` again on `Player`, which a Play from any view emits, and on `Sketch` and `Values`: a commit, a move of `x` or a drag's end leaves the monitored statuses, and a large sketch's diagnosis, to `tick()`. The sweep bar (`SweepBarPresenter`) plays and pauses through `App::toggle_play()`, as a range's sheet does: a retained sweep bar reads its rows again on `Model`, `Sweep` and `Player`.

### Scripted runs

`parse_script()` reads a script ([its commands](../reference/cli.md#scripts)) into steps, and `make_script()` puts the command line's `--set`, `--solve`, `--pareto` and `--tab` first; it also turns `--mouse`, `--drag`, `--click` and `--frames` into steps on the frames they have always used, which old scenes depend on. A front-end calls `ScriptPlayer::next()` before each frame: it runs the commands that go through the App (`open`, `select`, `action`, ...) and returns the frame's input, which the front-end queues in its toolkit; after drawing the frame, it writes the window to the frame's `shot`, if any. A scripted run must draw the same pixels every time: it keeps the `NullSettingsStore`, turns the solver's durations off with `SolverSession::set_show_durations(false)`, leaves the sketch diagnosis worker off (`SketchSession::set_worker()`), so that a large sketch is diagnosed at the next `tick()`, on the GUI thread, and advances the toolkit's clock by a fixed 1/60 s per frame. `--headless` plays it in the selftest's context, with the window's style and font at the script's size, so that the script's pixels are where a window has them; `--dump` writes `run_state()` when it ends. The `gui_scripts` test plays `tests/gui/*.script` headless and checks their dumps (`tests/gui/gui_scripts.cmake`).

`MainWindow::show()` runs one frame in a fixed order, which later code may depend on:

1. The menus, drawn before `show()` inside the main menu bar; a menu entry runs its action there.
2. The Global shortcuts, then `App::sync()`, which brings the selection up to date with the document, then the Panel shortcuts while a panel had the keyboard in the last frame.
3. The gesture safety net: a widget that disappears while held never reports its release, so when no item is active, `PropertiesPresenter::finish_drag()` ends a sheet's drag, then the Document's open gesture ends. A value typed into a drag field and not yet sent goes first (`send_typed_value()`): Tab between a pair's two fields leaves no item active for a frame.
4. `App::tick()`, then the scene.
5. The status bar, then the dockspace, which builds the default layout first when none was loaded, or a frame after Reset layout asked for it: the panels it opens again must have begun once, or a node would add their tabs after the others. Then the panel focus requests are queued; the panels take one per frame, since a dock node shows the tab of the focused window only when it next updates, and none while a popup is open, since `SetWindowFocus()` closes the popups over another window, a modal one included.
6. The canvas is not fed on the frame its window appears: the window does not have its docked size yet, and the start-up fit would take that rectangle.

The hovered row becomes the lists' hot key, the context menu opens when the canvas or a row asked for it, then the dialogs and the formula pop-up, and the layout is saved when ImGui reports a change; `~MainWindow()` saves it once more.

## What a new front-end implements

1. **A main loop** that owns an `App`, opens the instance, calls `tick()` (every frame, or from a timer while `busy()`), turns the sketch diagnosis worker on outside a scripted run (`app.sketch().set_worker(true)`), and sets the window title from `window_title()`. The window's close button asks `request_quit()`; the window closes once `quit_confirmed()` is true, which the Quit action and the answer to the unsaved-changes question set.
2. **`App::sync()` after each input**: once the actions and presenter operations an event ran are done, before anything reads the selection. It drops the entries that an Open, a Reload, an undo or an erase removed, and the display items after an undo or redo. Never call it from a `changed()` slot: a rename and the erasure of a display item fix the selection up after the document has changed, and a `sync()` in between deselects the entry.
3. **Menus and keys** from `App::menus()` and the registry: each entry's `label()`, the text of its first chord (`chord_text()`), `is_enabled()`, `is_checked()`, `run()`. The keys go through `ActionRegistry::run_pressed()`, given `App::key_focus()` of the scope, whether a text field has the focus and whether a dialog is open, the held modifiers, and whether a key went down: it applies the modifier, text-field, tool-field and dialog rules, so a toolkit's own accelerator matching must not replace it, nor a `KeyFocus` built by hand, which would let a unit's letter typed into a tool's field start a tool.
4. **The canvas**: pointer events translated to `PointerInput`, reporting one press at a time with its click count, and Space held; `set_viewport()` and `update()`; the Canvas actions while the pointer is over it; the characters typed while it has the pointer and no text field has the keyboard, to `CanvasController::typed()` (wxWidgets: `EVT_KEY_DOWN` goes to `run_pressed()`, then `EVT_CHAR` to `typed()`, which keeps a digit, `-`, `.`, `(` and `=` and drops a letter, so a letter starts its tool and a digit opens a value field; a wx key event goes to the window with the focus, not to the one under the pointer, so the canvas, a `wxWindow` with `wxWANTS_CHARS`, takes the focus when the pointer enters it and at a click, unless a value field of its own has it, or the digits typed over it would go to a list's type-ahead search); the modifiers of each pointer event, <kbd>Ctrl</kbd> being the tools' freehand; `build_canvas_display()` replayed on a `Painter`, given `App::hot()`, `SketchSession::scene()` and the active tool's `preview()`; a `TextMeasurer`; the hover text from `hover()`; the context menu of `context_actions()` where `take_context_menu()` asks for it. While a tool is active, on `App::changed()` with `Instance`, `Model` or `Sketch`, call `update()` again with the last input and no motion: the tool's re-feed after a commit (above), which no pointer event brings. When the pointer capture is lost, call `CanvasController::cancel_pointer()`: a design point's drag ends as one step, a sketch drag is dropped, a box or a pan stops, and the tool that had the press hears `Cancel` (wxWidgets: `EVT_MOUSE_CAPTURE_LOST`). The paint may take a newer `app.scene()` than the last `update()` was given: the handles are drawn from the scene the paint passes. It must take the scene as it stands after `update()`, the actions and `typed()`: a release commits a sketch drag, whose live scene goes, and a tool's click commits its shape, so a scene read before them draws the drawing as it was before the gesture, for one frame. The ImGui canvas reads `app.scene()` again after its input; an event-driven toolkit paints after the event that committed. `hover()` belongs to the pointer event, after `update()` and with the same scene.
5. **The toolbar**: a window or a toolbar beside the canvas over `App::toolbar()`, titled `kToolbarLabel`: a button per tool action (its `caption`, else its label), pressed while `is_checked()`, greyed while not `is_enabled()`, with its `tip` as tooltip, disabled or not; a check box per entry of a group whose `options` is set, the Options toggles, whatever its title says. A wxWidgets port can use a `wxAuiToolBar` pane (or a `wxToolBar`) with `wxITEM_CHECK` tools, `EVT_TOOL` calling `run()`, `EVT_UPDATE_UI` reading `is_enabled()` and `is_checked()`, `SetToolShortHelp()` from `tip()`, refreshed on `Tool` and `Instance`. **The value fields**: each `ValueField` of the active tool drawn at `view().to_screen(anchor)` beside it, over the canvas and inside it (on the anchor's other side near the canvas's right or bottom edge), the fields of one anchor stacked; a closed one shows `field_status()`, its text, tone and tooltip, and takes no click, which reaches the canvas and places a point. The field `editing()` names, or `take_field_focus()` asks the keyboard for, is a text field showing `editing()`'s text (a child `wxTextCtrl` with `wxTE_PROCESS_ENTER | wxTE_PROCESS_TAB`, moved on `Tool` and `View`). After each input event the view forwards, it takes `take_field_focus()` (`SetFocus()`) and `take_text_update()` (`ChangeValue()`, then `SetInsertionPoint()`, and `SetSelection()` of the whole text when `select` is set); a request raised, again or not, also emits `Tool`. `TextUpdate::caret` counts bytes, as `FormulaDraft`'s `caret()` does, where `SetInsertionPoint()` counts characters: `°` is two bytes. The field reports each edit with `set_field_text()` (`EVT_TEXT`), and <kbd>Enter</kbd>, <kbd>Esc</kbd> and <kbd>Tab</kbd> with `field_key()` from `EVT_KEY_DOWN` without `Skip()` (or the frame's `EVT_CHAR_HOOK` would also run `app.escape`), and gives the keyboard back to the canvas on any outcome but `Refused` and `None`. `EVT_KILL_FOCUS` does nothing: the host applies a text left in a field at the next press. Until the field has the keyboard, the canvas keeps sending its keys to `run_pressed()` and its characters to `typed()`, and the field reports the keyboard with `field_focused()` once it has it; a character or key the toolkit drops while the focus moves goes to the field or to `field_key()` itself (the ImGui view reads the characters of the frame the field takes the keyboard before its `InputText` consumes them and queues them again for the next frame, ahead of that frame's: given to `typed()` instead, they would reach the buffer after the next key's edit; it takes Enter and Esc on the next frame too, which `InputText` does not route yet).
6. **The formula pop-up**: a window over `FormulaDraft`, opened on `take_open_request()` and closed once `is_open()` is false, its field reporting `set_text()`, `set_caret()` and its keys to `key()`, showing `take_text_update()` and `candidates()`, its other fields over `fields()` and `set()`, `check()` and `refusal()` under them.
7. **A view per presenter**: the Solver tab (an adapter from `TablePresenter` to the toolkit's table), the Margins plots, the Messages (`activate(i)` on a click on a problem that has a `path`; the sketch message's line has `parts`, drawn on one line, a click on a part that selects something calling `activate(i, part)`), the sweep bar, and the status bar (`activate(i)` on a click on a segment that has a `link` or entries to `select`; the sketch message's segment is `Tone::Dim` while it is greyed, and "2 requirements violated" turns on the Constraints list's Violated filter). One list adapter over any `ListPresenter`, following its invalidation contract, and one property sheet over a `DetailSheet`, following the sheet contract and editing through `PropertiesPresenter`'s keyed operations, or `DocumentPresenter`'s for the Document panel. A list reports the entry of its hovered row with `set_hot(HotSource::List, ...)`, a right click on a row with `context_click()`, a click on a toggle with `toggle()`, a double click with `Panels::activate()`, and its filters' controls with `set_filter()`; a name editor commits with `PanelHost::rename()` and closes with `cancel_rename()`; each panel takes `PanelHost::take_rename_request(panel)` and `take_reveal(panel, key)`, and each text field `take_field_focus(path)`.
8. **Docking** (wxAUI): a window for the canvas, one for the toolbar beside it, which no menu closes, and one per `PanelId`, a default layout, the open panels from `panel_open()` and a closed one reported with `set_panel_open()`, the panel that has the keyboard reported with `set_focused_panel()`, the requests `take_panel_focus()`, in their order, and `take_layout_reset()`, the layout saved with `save_layout()` under the toolkit's own key and loaded with `load_layout()`. A scripted run keeps the `NullSettingsStore`.
9. **The dialogs**: take each open request and answer it. A native save dialog asks before replacing a file, then passes `PathDialog::Replace::Confirmed` to `submit()`.
10. **A theme**: a colour for every `Tone` and every canvas `Role`, the sketch's `Element`, `ElementHelper` (grey) and `ElementFixed`, and the tools' `Preview` and `Suggestion` included.
11. **Change handling**: subscribe to `App::changed()` and refresh what each bit names.
12. **Scripted runs**, to check its pixels: a `ScriptPlayer` stepped before each frame, its input fed to the toolkit, the shots written after the frame, a fixed time step.

The front-end's own glue (input translation, key mapping, what the toolkit reports while a widget is held) gets its own tests, as `--selftest` does for ImGui.

## Changing the GUI

- **New behaviour or state**: in `gs_app` (a presenter, `App`, an action), with a `test_app` case in `tests/app/`. The sources of `gs_app` and `test_app` are found by glob: run CMake's configure step after adding a file.
- **A new command**: an `Action` in `App::add_actions()`, listed in a menu of `menus_` when it has one. The front-end needs nothing more. A new tool is a `Tool` (a `StateTool` for one placed state by state) that `App` provides for its `tool_specs()` id with `ToolHost::provide()`; its action, chord and toolbar button exist already, and it is in no menu. `sketch.solve` and the sketch edits (`sketch.merge`, `sketch.detach`, `sketch.delete_vertex`, `sketch.unfix`, `sketch.driving`, `sketch.reference`, `sketch.flip_side`) are in no menu: an entry there would change the Edit menu of every file; the context menu lists them while they are enabled, for a file with a sketch. A sketch edit is enabled by the kind of the selection (two points, a slot, a constraint with a side, a dimension for `sketch.reference`), not by whether it applies: run, it says why not in the notice, as the select-first mode of the constraint tools will.
- **A new widget or layout**: in the front-end view only, calling the presenter.
- **Check pixels** with the scenes of `tools/screenshots/scenes`, scripts that the GUI plays in a window drawn offscreen, writing PPM images. Render them before and after a change, and compare:

    ```bash
    tools/screenshots/render.sh build/geomsolver /tmp/scenes-before
    # change, rebuild
    tools/screenshots/render.sh build/geomsolver /tmp/scenes-after
    tools/screenshots/compare.sh /tmp/scenes-before /tmp/scenes-after
    ```

    `render.sh GEOMSOLVER OUT_DIR [SCENE...]` plays every scene, or the named ones, from the repository root, where their instance paths start. It gives the runs an empty temporary `XDG_CONFIG_HOME` and fails when a run leaves anything there: a scripted run never touches the user's settings. `compare.sh REF_DIR NEW_DIR` compares two sets byte for byte and prints the bounding box of each difference. Rendering needs a display, like the GUI itself. A scripted run draws the same pixels every time, on a loaded machine too: its clock moves by 1/60 s per frame, and the solver's durations print as `—`. A change that only moves code between the layers must give byte-identical images.

    A scene's input is in window pixels, which a change of layout moves. When it does, re-aim the scene: keep pixels for the input the scene is about, and reach the rest through `select`, `action` and `panel`, which go through the App ([script commands](../reference/cli.md#scripts)). A single image needs no script: `build/geomsolver tests/data/tv_corner_ref.json --screenshot overview.ppm`.

    One difference is not a regression. ImGui bakes a glyph into its font atlas the first time the glyph is drawn or measured (`CalcTextSize` counts), so code that measures text in another order moves glyphs in the atlas: `build_canvas_display()`, for one, measures every label through the `TextMeasurer` before the painter draws the grid's digits. The images then differ only on the edges of a few glyphs, by at most about 5/255, the same way on every run, with nothing displaced. To confirm it, measure the printable ASCII range (32 to 126) with `CalcTextSize` right after the first `ImGui::NewFrame()` in both binaries: the images must then be identical.

    A refactor that must not change what the GUI draws is checked against a reference set: the scenes rendered by the commit before it. Render both sets on the same machine: the pixels come from its OpenGL driver, and another one may draw the edges of shapes and glyphs differently.

- **Update the screenshots of the documentation** when a change shows in them. Every PNG of `docs/assets/screenshots` is a scripted run, and `tools/screenshots/docs.sh` makes them all again:

    ```bash
    tools/screenshots/docs.sh build/geomsolver
    git status docs/assets/screenshots
    ```

    The manifest at the top of `docs.sh` gives, for each PNG, the script that draws it, from `tools/screenshots/docs` or `tools/screenshots/scenes`, the shot it takes there, and the part of the window it keeps. Each script runs once, as `render.sh` runs a scene, and may take several shots, named by `shot`; a doc script reaches the state it shows through `open`, `solve`, `select`, `action` and `panel`, types a sweep value into its slider after a <kbd>Ctrl</kbd>-click, and moves the pointer away from what it dragged, which would stay highlighted. `ppm2png.py IN.ppm OUT.png [X Y W H]` crops the shot and writes the PNG with Python's standard library alone, the same bytes for the same pixels, so a screenshot that did not change shows no difference in git: look at each one that did, and at its alt text, which describes what the image shows. A new screenshot is a script, or a shot in one, a line of the manifest and the image on its page. `docs.sh --check`, which the `docs_screenshots` test runs, fails when a page shows a PNG the manifest does not make, when the manifest makes one that no page shows, or when `docs/assets/screenshots` holds a file the manifest does not make.

Run the whole suite as described in [Installation](../getting-started/index.md); while you work on the GUI logic, `build/test_app` runs alone.
